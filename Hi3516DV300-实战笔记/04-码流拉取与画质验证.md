# 04｜码流拉取与画质验证（ffmpeg/ffprobe 在裸流上的陷阱）

> 目标：把板子上的 H.265/H.264 裸流拿到 PC 分析，判断画质能不能用、要不要 IQ 调参
> 关键教训：**裸流（ES）没有时间戳，ffprobe 报的 25fps 是猜的，duration 是 N/A**

---

## 1. 取流链路

```
板子 VENC → stream_chn0.h265（写文件）
   │ tftp -p 上传
   ▼
VM /srv/tftp/board.h265
   │ ffmpeg / ffprobe
   ▼
抽帧 JPG / 统计帧数 / 看解码错误

板端（注意：**别写在 jffs2 上**，原因见第 5 篇）：

tftp -p -l stream_chn0.h265 -r board.h265 192.168.1.103
```

### 1.1 先认识码流：NAL、I/P/B、GOP、SPS/PPS

拿到一个 `.h265`/`.h264` 文件，先知道它是什么结构，后面所有分析才有依据。

#### ① 裸流就是 NAL 单元首尾相接

**Annex-B** 格式（海思 VENC 默认输出）用起始码分隔每个 NAL：

```
00 00 00 01  67 ...  ← SPS
00 00 00 01  68 ...  ← PPS
00 00 00 01  65 ...  ← IDR 帧（关键帧）
00 00 00 01  41 ...  ← P 帧
00 00 00 01  41 ...  ← P 帧
```

| 标准 | 起始码 | 头长度 |
|---|---|---|
| H.264 | `00 00 00 01` 或 `00 00 01` | 1 字节（含 5bit type） |
| H.265 | `00 00 00 01` 或 `00 00 01` | **2 字节**（type 在第一个字节的 6bit 里） |

> H.265 的头是 2 字节，这正是第 6 篇里"大佬 RTSP 只支持 H.264"的原因——他的解析代码按 H.264 的 1 字节头写的。

#### ② NAL 类型：几个必须认得的

**H.264**

| type | 名称 | 作用 |
|---|---|---|
| 1 | non-IDR slice | P/B 帧的图像数据 |
| 5 | IDR slice | **关键帧**，可独立解码，GOP 起点 |
| 6 | SEI | 附加信息（有些封装把时间戳塞这里） |
| 7 | **SPS** | 序列参数集：分辨率、profile、**帧率**、位深 |
| 8 | **PPS** | 图像参数集：量化表、熵编码方式 |

**SPS/PPS 为什么关键**：

- 解码器必须先拿到 SPS/PPS 才能初始化（不知道分辨率就没法分配缓冲）
- RTSP 的 SDP 里 `sprop-parameter-sets` 就是它们的 base64（第 6 篇那个假串 `AAABBCCC` 就在这）
- 录像文件如果开头丢了 SPS/PPS，**整个文件播不了**（典型事故）

#### ③ I / P / B 帧

| 类型 | 参考关系 | 典型大小（1080p） | 说明 |
|---|---|---|---|
| **I** | 不参考任何帧 | 最大，**135 KB** | 完整图像，可独立解码 |
| **P** | 参考前面的帧 | 小，**12 KB** | 只存差异 |
| **B** | 参考前后帧 | 最小 | **延迟大，监控基本不用** |

海思 VENC 默认不开 B 帧（为了低延迟），所以你的码流里只会有 I 和 P——**用 `ffprobe -show_packets` 看 flags 只有 `K_` 和 `__` 就对了**。

#### ④ GOP：两个 I 帧之间的距离

```
I  P P P ... P  I  P P P ... P  I
|---- GOP = 30 ----|
```

| GOP 设置 | 优点 | 缺点 |
|---|---|---|
| 小（如 15） | 随机接入快、开流快、抗丢包 | 码率高（I 帧大） |
| 大（如 60） | 码率低、画质好 | 开流慢，丢一个 I 帧要等很久才能恢复 |
| 监控常规 | **25~50（约 1~2 秒）** | 平衡 |

判据：`I 帧数 × GOP ≈ 总帧数`。本次 594 帧 / 20 个 I 帧 → GOP=30，与 sample 里设的 30 完全吻合 ✓

#### ⑤ 码率控制三种模式（sample 启动时让你选的）

| 模式 | 行为 | 适合 |
|---|---|---|
| **CBR**（`c`） | 恒定码率，靠调 QP 硬顶 | 网络带宽固定、要可预测 |
| **VBR**（`v`） | 恒定质量，码率随画面复杂度浮动 | 本地录像、画质优先 |
| **AVBR** | 自适应，兼顾两者 | 绝大多数监控场景 |

`QP` 是量化步长，越大压缩越狠、画质越差。看到"马赛克/块效应"先查 QP 是不是被码率逼高了。

## 2. 裸流分析的正确姿势

### 2.1 先数帧数（唯一可靠的"多少帧"）

```bash
ffprobe -v error -count_frames -select_streams v:0 \
        -show_entries stream=nb_read_frames -of default=nw=1:nk=1 board.h265
# 594
```

配合**已知录制时长**才能算真实帧率：

```
真实 fps = 帧数 / 录制秒数 = 594 / 20 = 29.7 fps
```

### 2.2 不要相信 avg_frame_rate / duration

```
$ ffprobe -show_entries stream=avg_frame_rate,duration board.h265
avg_frame_rate=25/1        ← ffmpeg 假设的默认值，不是真实帧率
duration=N/A               ← ES 流没有容器，无时长信息
r_frame_rate=25/1
```

**H.265/H.264 裸流（Annex-B）里只有 NAL 单元，没有 PTS/DTS**。ffmpeg 只能按默认 25fps 编时间轴，所以：
- `fps=1` 抽帧抽到几张，只反映"假想时间轴有几秒"，**不能反推真实时长**
- `duration=N/A` 是正常现象，不是文件坏了

本次就被这个坑误导过：30 秒录制用 `fps=1` 只抽出 5 张，一度以为码流只有 5 秒。

### 2.3 看解码错误（判断文件是否完整/损坏）

```bash
ffmpeg -v error -i board.h265 -f null - 2>&1 | head -20
# 无输出 = 解码干净
```

如果输出 `out of range intra chroma pred mode`、`error while decoding MB` 之类，先怀疑**文件不完整**（tftp 传一半就断了）。判据：文件大小是否与板端一致。

```bash
# 板端
ls -l /mnt/stream_chn0.h265
# VM
ls -l /srv/tftp/board.h265       # 必须完全一致
```

### 2.4 看 GOP 结构（判断编码器是否正常）

```bash
ffprobe -v error -show_packets -show_entries packet=size,flags -of csv=p=0 board.h265 | head -20
```

典型健康输出（1080p H.265，GOP=30）：

```
138792,K_      ← I 帧，约 135KB
 37463,__      ← P 帧，切换后第一帧
 15016,__
 12178,__
 12544,__      ← 稳定在 12KB 左右
 ...
```

判据：
- I 帧数量 ≈ 总帧数 / GOP → 594 帧、6 I 帧 ≈ GOP 100 左右？实际本次 20 个 I 帧，对应 GOP=30
- P 帧大小稳定 → 编码器工作正常
- 若 P 帧全是几 KB 且连续 → 画面静止/曝光异常

## 3. 抽帧看画质

```bash
mkdir -p frames
ffmpeg -i board.h265 -vf fps=1 frames/f_%02d.jpg
```

或者只取首帧：

```bash
ffmpeg -i board.h265 -frames:v 1 -q:v 2 first.jpg
```

> `fps=1` 的含义是"每 1 秒（按 ffmpeg 假想时间轴）取 1 帧"，用于**看画质**足够；不要用它判断时长。

## 4. 画质评估（GC2053 + 无 IQ 文件）

实拍场景：室内天花板 + 吊扇（白墙为主）。

| 指标 | 观察 | 结论 |
|---|---|---|
| 白平衡 | 白墙不发绿、不发紫 | ✅ 正常 |
| 曝光 | 亮度适中，无明显过曝/欠曝 | ✅ 正常 |
| 噪点 | 暗部有轻微噪点，可接受 | ✅ 可接受 |
| 清晰度 | 可辨吊扇叶片纹理 | ✅ 可接受 |

**结论：GC2053 用 SDK 默认 ISP 参数（无 IQ ini）画质可用，IQ 文件缓办。**

补充证据：资料包里只有 imx327/imx335 的 IQ ini，**没有 GC2053 的**；板端 `/etc/sensors/` 也是空的（`find *.ini` 无结果）。想调 IQ 得找厂商要。

## 5. 单帧快速验证（不落盘路线）

如果只是想知道"到底有没有图"，不必走 tftp：

```bash
# 板端直接看文件是否在长
ls -l stream_chn0.h265; sleep 3; ls -l stream_chn0.h265
```

增长率参考：1080p H.265 CBR 4Mbps ≈ **500KB/s**（本次实测 10,115,098 字节 / 20 秒）。
若只有几十 KB/s → 立即去看 `/proc/umap/venc`（见第 5 篇）。
