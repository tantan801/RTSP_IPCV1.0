# Hi3516DV300 项目总览：一条链路 + 一本词典

> 目的：**一篇文章说清"这个项目做了什么、怎么做的、为什么这么做"**，并把 01–11 篇里出现过的所有专属词收进词典。
> 读法建议：先看 §0 一页图 → §1 总流程 → §3 遇到不认识的词再查 → §4 看设计取舍。

---

## 0 一页看懂

### 0.1 这个项目是什么

在 Hi3516DV300 开发板上，从零搭出一条**能开机自启、能远程实时观看、画面上带时间水印、能实时框出人形**的网络摄像头链路。

```
一颗 GC2053 摄像头 → 板子采集编码 → 标准 RTSP 协议推流 → 电脑 VLC 直接打开就能看
                                                            ↑
                                              画面左上角有走动的北京时间水印
```

对外就一句：**"VLC 打开 `rtsp://192.168.1.20:554/live` 就能看到带时间水印的实时画面"**。市面上的 IPC（网络摄像头）干的就是这件事，本项目是把它从零做了一遍。

### 0.2 硬件与软件底座

| 项 | 值 | 说明 |
|---|---|---|
| 主控 | Hi3516DV300 | 与 Hi3516CV500 **同一颗 die**，共用一份 SDK，所以 `ko` 全叫 `hi3516cv500_*` |
| Sensor | GC2053（200 万像素） | 1080p，MIPI 2 lane 输出 |
| 内存 | DDR 1GB | `-osmem 128` 给 Linux（≈121MB），其余 896MB 是 MMZ（媒体专用） |
| 存储 | 27MB jffs2 根分区 | 小、慢、怕写满——这是后面好几个 bug 的根源 |
| SDK | Hi3516CV500_SDK_V2.0.2.0 | MPP、sample、NNIE 例程都在里面 |
| 工具链 | arm-himix200-linux | 交叉编译，不在非交互 PATH 里，跑 make 要手动 export |
| 网络 | 板 `192.168.1.20`、PC `192.168.5.88/16`、网关 `192.168.3.1` | 板子掩码必须 `/16`，见第 11 篇 |

### 0.3 整条链路一张图

```
 ┌─────────┐   ┌────────┐   ┌────┐   ┌──────┐   ┌────────┐   ┌──────┐   ┌────────┐
 │ GC2053  │──▶│ MIPI   │──▶│ VI │──▶│ VPSS │──▶│  VENC  │──▶│ RTSP │──▶│  VLC   │
 │ sensor  │   │ RX(PHY)│   │    │   │      │   │ H.264  │   │ RTP  │   │ 播放器  │
 └─────────┘   └────────┘   └────┘   └──────┘   └────────┘   └──────┘   └────────┘
   出 RAW       串行差分      收数据   缩放/格式   压缩成码流    切包发送     解码显示
                              +ISP     转换                  UDP 单播
                                        │
                                        └─▶【OSD 时间水印在这里合成】→ 烙进码流

 旁路（已上线，第 12 篇）：
 VPSS chn2 (320×320 NV21) ──▶ Mmap 取帧 ──▶ CPU 转 BGR 300×300 ──▶ NNIE SSD 推理
                                                                  │
        水印层(layer=2) ─────────────────────────────────────┐    ▼
                                                            └─▶ RGN overlay(layer=1) 红框 ──▶ VENC 合成
```

**最重要的一句话**：这条链路上每一级都是**硬件单元**，CPU 只在两端（配置参数、发送网络包）参与。理解这一点，才知道为什么要 `bind`、为什么帧不算 malloc。

## 1 总流程：按数据流走一遍

每个阶段都标了"做什么 / 参数在哪 / 出问题长什么样"，这是排查时的导航图。

| # | 阶段 | 做什么 | 关键参数/接口 | 失败的表现 |
|---|---|---|---|---|
| 1 | 上电加载驱动 | 加载 MPP 各 `.ko` + 划分 MMZ | `S00devs` → `load3516dv300 -i -sensor0 gc2053 -osmem 128 -total 1024` | 无 `/dev/hi_mipi`，`lsmod` 少一堆 |
| 2 | Sensor 初始化 | 通过 I2C 配寄存器，MIPI 起流 | `sample_comm_vi.c` 的 `lane_id`、`LANE_DIVIDE_MODE`；sensor 用户态库 `libsns_gc2053.so` | MIPI 无 DETECT INFO；图全绿/全黑 |
| 3 | VI 采集 | 收 MIPI 数据，ISP 做 3A/去马赛克/降噪 | DEV/PIPE/CHN 三级属性 | `vi` 的 `IntCnt` 不涨 |
| 4 | VPSS 处理 | 一分多：主码流 1080p + 子码流 720p + 检测图 320×320 给 NNIE | `stSize[]`、`abChnEnable[]` | 通道使能失败；下游取不到帧 |
| 5 | VENC 编码 | 把 YUV 压成 H.264/H.265 码流 | 通道属性、GOP、码率 CBR 4Mbps | `Sequence` 不涨、`Full` 涨（输入被堵） |
| 6 | 取流 | 从 VENC 拿 `HI_MPI_VENC_GetStream` | `sample_comm_venc.c` 的取流线程 | `0xa0088012`、`Current frame is NULL` |
| 7 | RTSP 发送 | 打包成 NALU → FU-A 分片 → RTP → UDP | 554 端口、`marker`、时间戳 90000/帧率 | SDP 有、RTP 没包；VLC 黑屏 |
| 8 | OSD 叠加 | 在 VENC 前合成时间水印 | `HI_MPI_RGN_*`，ARGB1555，200×40 | 画面无水印；字镜像/撕裂 |
| 9 | 开机自启 | init 脚本拉起 + 守护重启 + 网络/时钟自愈 | `S99rtsp`（166 行） | 重启后没进程 / 没路由 / 时间 1970 |
| 10 | 智能分析（已完成） | VPSS chn2 出 320×320 → Mmap 取帧 → NNIE SSD → 画红框 overlay | `nnie_detect.c`、RGN layer=1 | 段错误 rc=139（内核地址）；框不动；水印被盖 |

### 施工顺序为什么是这个顺序

实际动手是：**先出图 → 再固化 → 再取流验画质 → 再推流 → 再叠字 → 再设备化 → 最后 AI**（AI 已完成，见第 12 篇）。

理由是一条硬规则：**每一级都必须先看到"上一级的输出是对的"，才往下走**。反例代价极大：如果先接 RTSP 再查 MIPI，VLC 黑屏时你无法判断是"没出图"还是"推流坏了"。这也是第 11 篇排障时"从下往上、一层验完再上一层"的同一个道理。

## 2 技术栈分层：每层用什么、做什么、为什么

| 层 | 技术/组件 | 干了什么 | 为什么选它 |
|---|---|---|---|
| 光学/采集 | GC2053 + MIPI CSI-2 | 光电转换、串行差分传输 | 板子自带的 sensor；MIPI 是移动端事实标准，2 lane 够 1080p30 |
| 采集驱动 | MPP VI + ISP | 收 RAW、3A、去马赛克 | 海思把 ISP 做进硬件，CPU 不参与，功耗低 |
| 处理 | MPP VPSS | 缩放、格式转换、一分多 | 一次采集多路输出，避免重复采集 |
| 编码 | MPP VENC | H.264 压缩 | 硬件编码，1080p30 只占几个百分点 CPU |
| 传输 | 自研 RTSP server + RTP/UDP | 信令 + 打包发送 | SDK 无 RTSP；第三方 live555 太重且功能受限 |
| 叠加 | MPP RGN（OVERLAY） | 在编码前把位图烙进画面 | 客户端无关、无法关闭，NVR/录像都自带 |
| 智能 | NNIE + `.wk` 模型 | 硬件神经网络推理 | 专用 NPU，比 CPU 快一个量级，几乎不占 CPU |
| 存储 | tmpfs（`/mnt`）+ jffs2（根） | 日志/锁放内存，程序放 flash | jffs2 写满会反压整条采集链（第 05 篇的血案） |
| 系统 | busybox init + `rcS` + `S??` 脚本 | 开机自启、守护、网络、对时 | 精简 rootfs 没有 systemd，只能这么来 |
| 工具 | telnet + Python 自动化 | 远程执行、批量验证 | 板子没有 ssh；手工敲命令无法保证一致性 |

## 3 概念词典（按主题分组）

> 用法：Ctrl+F 搜词。每条给"是什么 + 在本项目里为什么和它打交道"。

### A. 光学与采集

| 词 | 是什么 | 在本项目里 |
|---|---|---|
| **Sensor** | 图像传感器，把光转成电信号 | GC2053，1080p，输出 RAW Bayer |
| **RAW Bayer** | 每个像素只有一个颜色分量（R/G/B 交错），需"去马赛克"还原 | ISP 的输入；RAW 不能直接编码 |
| **RAW10 / RAW12** | 每个像素 10/12 bit 精度 | 配错位深 → 颜色发灰/发绿 |
| **MIPI CSI-2** | 摄像头串行接口标准，用差分 lane 传数据 | 板子走 2 lane |
| **Lane** | 差分数据通道，一条 lane 一对线 | GC2053 用 2 条；`lane_id` 决定映射 |
| **lane_id** | 告诉 MIPI 控制器"物理第几条 lane 接到哪" | 本板必须 `{0,2,-1,-1}`：用了 lane0 和 lane2，不是 0 和 1 |
| **lane_divide_mode** | 一个 MIPI 控制器如何切分给多个 sensor | 本板只能 `LANE_DIVIDE_MODE_1`（2+2 分割），否则起不来 |
| **MIPI RX (PHY)** | 物理层接收器 | `cat /proc/umap/mipi_rx` 看 DETECT INFO 判断有没有收到信号 |
| **I2C / 0x37** | Sensor 的寄存器控制总线与地址 | 初始化失败先看 I2C 能不能读到 ID |
| **ISP** | 图像信号处理器：3A、去马赛克、降噪、宽动态 | 硬件模块，参数由 IQ 文件调 |
| **3A** | AE 自动曝光 / AWB 自动白平衡 / AF 自动对焦 | GC2053 定焦，实际只有 AE+AWB |
| **WDR** | 宽动态，明暗兼顾 | 默认关；强逆光场景才需要 |
| **IQ 文件** | ISP 的调参文件（各家私有格式） | 本项目没有，用默认参数，画质够用 |
| **曝光时间 / 行时间** | 感光时长由"行数 × 行时间"决定 | 帧率被曝光时间封顶，暗光下帧率会掉 |
| **Sensor 用户态库（`.so`）** | 海思把 sensor 驱动做成用户态库，不是内核模块 | 换 `libsns_gc2053.so` 就能改出图行为（厂商 2021 版修复了问题） |
| **DETECT INFO** | `mipi_rx` 里报告"检测到什么格式/多少 lane" | 出图第一判据：没有它 = 物理层没通 |

### B. 海思 MPP 模型

| 词 | 是什么 | 在本项目里 |
|---|---|---|
| **MPP** | Media Process Platform，海思对整条硬件流水线的软件封装 | 所有 `HI_MPI_*` API 都属于它 |
| **VI** | Video Input，接收 MIPI 数据并做 ISP | 采集入口 |
| **VPSS** | Video Process Sub-System，缩放/格式转换/一分多 | 主码流 1080p、子码流 720p、检测图 320×320 都从这里出 |
| **VENC** | Video Encoder，硬件编码器 | 出 H.264 码流 |
| **VGS** | Video Graphics，纯硬件缩放/格式转换/拼接 | 无通道概念，一次性调用；NNIE 前的格式转换可用 |
| **VO** | Video Output，送屏（HDMI/BT1120/MIPI 屏） | 本项目不用；NNIE 例程用来显示 |
| **NNIE** | 神经网络推理加速器（硬件 NPU） | 检测链路的主角（第 12 篇） |
| **DEV / PIPE / CHN** | VI 的三级模型：物理接口 → 处理管线 → 输出通道 | 排障时先判断错在哪一级，别瞎改结构体 |
| **Grp / Chn** | VPSS 的组织方式：一个组（Grp）下挂多个物理通道（Chn） | `VPSS_MAX_PHY_CHN_NUM = 3`，所以最多 3 路 |
| **bind（绑定）** | 用 `HI_MPI_SYS_Bind` 把两级硬件接起来 | 帧在硬件内部流转，一个字节不过 CPU → CPU 占用极低 |
| **user mode（用户态取帧）** | 解绑，自己 `GetChnFrame` 拿帧 | NNIE 必须这样；取完**必须 Release** |
| **GetChnFrame / ReleaseChnFrame** | 取帧 / 还帧 | 忘记 Release = VB 池被抽干 = 全链丢帧 |
| **主码流 / 子码流** | 同一路图像编两份（1080p 高清 + 720p 流畅） | 手机预览用子码流省带宽，NVR 录像用主码流 |
| **帧率控制** | VPSS 可以按比例丢帧 | 下游吃不消时的一种保护 |

### C. 内存（最容易出事的地方）

| 词 | 是什么 | 在本项目里 |
|---|---|---|
| **MMZ** | Media Memory Zone，从 DDR 划走的媒体专用内存区，Linux 看不见 | 896MB；所有图像帧从这里分配 |
| **osmem / total** | `load3516dv300 -osmem 128 -total 1024` 的两个参数 | 128MB 给 Linux，1024 是总 DDR 容量 |
| **VB（Video Buffer）** | 装图像帧的内存块，大小由分辨率和格式决定 | 1080p NV12 一块 ≈ 3.11MB |
| **VB 池（Pool）** | 一批同规格 VB 块 + 分配器 | 本项目 48MB 池、10 块；运行稳态用 5 块 |
| **VbFail** | VI 申请不到 VB 块 | 计数器涨 = 下游不还块（反压）或池太小 |
| **`/proc/media-mem`** | 看 MMZ 总用量/剩余 | 判断"够不够开一路 NNIE" |
| **SEG / LINE 压缩** | 海思的图像内存压缩，省的是 **DDR 带宽**，不是空间 | VB 块仍按不压缩的最大值分配，别算错 |
| **DDR 带宽** | 内存读写总吞吐 | 4K 或多路时先撞这个墙，不是容量墙 |
| **tmpfs** | 内存文件系统，掉电即丢 | `/mnt` 48MB；日志、锁、临时码流都放这 |
| **VB_REMAP_MODE_NONE** | 系统配置项：VB 块**不**做用户态重映射 | 此时 `stVFrame.u64VirAddr` 给的是**内核虚拟地址**，用户态解引用必 SIGSEGV（rc=139） |
| **HI_MPI_SYS_Mmap** | 用物理地址在用户态映射一段内存 | 取帧后读数据必须自己 Mmap，用完 Munmap——这是 S2 最大的坑 |
| **jffs2** | 面向 flash 的日志式文件系统 | 根分区 27MB；**写满会让写延迟飙到秒级**，反压全链 |
| **ext4 / NFS / SD** | 其他可选存储 | 长期录像要放 SD/NFS，绝不写 jffs2 |

### D. 编码与码流

| 词 | 是什么 | 在本项目里 |
|---|---|---|
| **H.264 / H.265** | 视频压缩标准 | 本项目 H.264（H.265 同带宽画质更好但兼容性略差） |
| **NALU** | 编码器输出的最小数据单元 | 一帧 = 若干 NALU（SPS/PPS/IDR/P 各是 NALU） |
| **SPS / PPS** | 参数集 NALU，描述分辨率、帧率等 | 解码器必须先拿到才能解；缺了就黑屏 |
| **I 帧 / IDR** | 完整帧，不依赖其他帧 | GOP 起点；丢 I 帧会导致长时间花屏 |
| **P 帧** | 只记录与前一帧的差异 | 体积小，但依赖链断了就花 |
| **GOP** | 两个 I 帧之间的帧数，本项目 30（每秒一个 I 帧） | GOP 大省带宽，但随机接入慢、丢包恢复差 |
| **CBR / VBR** | 恒定码率 / 可变码率 | 本项目 CBR 4Mbps，网络传输更可预测 |
| **PTS** | 显示时间戳，帧的"该什么时候显示" | 时基在 `VB_FRAME.u64PTS`，不在文件里 |
| **VencInt** | VENC 中断计数，等于编码了多少帧 | 判断"编码器到底在不在干活"的第一判据 |
| **Sequence** | VENC 通道已编码帧序号 | 重启后归零，用于确认是否在增长 |

### E. 传输协议

| 词 | 是什么 | 在本项目里 |
|---|---|---|
| **RTSP** | 实时流控制协议，管"会话"（DESCRIBE/SETUP/PLAY/TEARDOWN） | 端口 554；相当于点菜的对话 |
| **RTP** | 实时传输协议，真正装视频数据的包 | UDP 单播；相当于上菜 |
| **RTCP** | RTP 的控制搭档，做丢包统计/反馈 | 本项目简化未实现（VLC 能容忍） |
| **SDP** | 一段文本"菜单"，描述编码、分辨率、时钟 | DESCRIBE 的响应体 |
| **sprop-parameter-sets** | SDP 里带 SPS/PPS 的字段（base64） | 客户端连上就能解，不用等 I 帧 |
| **clock rate 90000** | RTP 时间戳的虚拟时钟，视频固定 90000 滴/秒 | 30fps 时每帧增量 = 3000；写错就慢放/快放 |
| **marker 位** | RTP 头标志，置 1 表示"这一帧最后一个包" | 解码器靠它判断整帧收齐 |
| **FU-A** | H.264 的 RTP 分片规则：大 NALU 拆成多包 | 一个 NALU 十几 KB，MTU 只有 1500 |
| **MTU / 1400B** | 单个网络包能装的有效载荷上限 | 分片大小按 1400 留余量 |
| **UDP / TCP** | 无连接 / 有连接 | 本项目 UDP（低延迟），TCP 模式也实现了 |
| **单播 / 组播** | 一对一 / 一对多 | 本项目单播 |
| **RTSP 方法** | OPTIONS / DESCRIBE / SETUP / PLAY / TEARDOWN | 五个方法就构成一次完整会话 |
| **ONVIF** | 设备互通标准（发现、能力、PTZ、录像） | 企业级 IPC 必备，本项目未做 |
| **GB/T 28181** | 国标，接入公安/政府平台 | 企业级项目常见硬需求 |
| **GB 35114** | 视频信息安全标准（签名/加密） | 政府项目合规要求 |
| **WebRTC** | 浏览器原生低延迟方案 | RTSP 的现代替代品之一（需转封装） |
| **live555** | 老牌开源 RTSP 库 | 资料包里有 demo，但功能受限、体积大，最终没用 |

### F. OSD 与叠加

| 词 | 是什么 | 在本项目里 |
|---|---|---|
| **OSD** | On-Screen Display，画面上的叠加文字/图形 | 左上角时间水印 |
| **RGN（Region）** | MPP 里的"贴图层"对象 | Create → SetBitMap → AttachToChn → Detach → Destroy |
| **OVERLAY_RGN** | 走芯片内部 overlay 硬件，块数少但最快 | 本项目用它（只要一块 200×40） |
| **OVERLAYEX_RGN** | 走 VGS，块数多、稍慢 | 大量/大尺寸叠加时才用 |
| **ARGB1555** | 每像素 16 位：1 位 alpha + R5G5B5 | OSD 位图的格式 |
| **FgAlpha / BgAlpha** | 前景/背景 alpha，范围 **[0,128]**（不是 255！） | 半透明靠它，不是靠 1 位 alpha |
| **衬板** | 文字下面那块半透明黑底 | 用 `0x0000` 像素 + 黑 BgColor 实现，不用真画矩形 |
| **Canvas 数（u32CanvasNum）** | 画布数量，1 张易撕裂，2 张双缓冲 | 本项目 =2 |
| **撕裂** | 画面一半旧字一半新字 | 画布数不足或写入时机不对 |
| **点阵字体** | 每个字符固定像素矩阵（本项目 8×16） | 95 字符 × 16B = 1520 字节，零依赖 |
| **MSB-first** | 字节最高位对应最左像素 | 写反了字会左右镜像 |
| **Attach / Detach** | 挂接 / 摘除 | 顺序错了 Destroy 会失败 |
| **贴 VENC vs 贴 VPSS** | 出口画一次 / 源头画一次 | 本项目贴 VENC chn0（只主码流带水印，改动最小） |
| **多 overlay 合成（u32Layer）** | 一块 VENC 通道可挂多层 RGN，layer 值**大的在上层** | 水印 layer=2、检测框 layer=1——反了水印就被盖掉 |
| **透明像素替换下层** | 本平台的合成不是标准 alpha：上层 A=0 的像素**不露出下层，而是替换** | 所以全屏画框布必须以"整体层序"保证水印在上，不能靠透明底"透视" |

### G. 智能（NNIE）

| 词 | 是什么 | 在本项目里 |
|---|---|---|
| **NNIE** | 海思的神经网络推理**硬件单元** | 不是算法、不是模型，是 NPU |
| **`.wk` 模型** | NNIE 专用的模型文件格式 | 由 `nnie_mapper` / RuyiStudio 转换生成 |
| **nnie_mapper / RuyiStudio** | PC 端模型转换工具 | **不在 SDK 里**，换自有模型要另找 HiSVP_PC 包 |
| **SSD** | 单阶段目标检测网络 | 例程自带，26MB；20 类通用检测 |
| **Prior Box** | SSD 预设的候选框（多尺度网格） | 12 个输出节点 = 6 组尺度 × 2（框+分类） |
| **阈值 / NMS** | 置信度过滤 / 非极大值抑制去重叠框 | 后处理在 ARM 上做，NNIE 只出原始结果 |
| **class 15 = person** | SSD 20 类里的"人" | 所以现在能当"人形检测"用，但不专用 |
| **300×300×3** | SSD 的输入尺寸与通道 | 实测确认：U8、RGB planar、C=3 |
| **YUV→RGB** | VPSS 出 YUV420SP，模型吃 RGB planar | 必须自己转，不能直接喂 |

| 词 | 是什么 | 在本项目里 |
|---|---|---|
| **busybox** | 精简版 Unix 工具集合 | 板子上的 `ls/cat/grep/sed` 都是它，语法略有差异（如 `cat -n` 不支持） |
| **init / rcS** | 第一个用户态进程 / 启动脚本总入口 | `rcS` 遍历 `/etc/init.d/S[0-9][0-9]*` 依次执行 |
| **S00devs** | 建设备节点 + 加载 MPP 驱动 | 固化 `-sensor0 gc2053 -osmem 128 -total 1024` |
| **S80network** | 配 IP | 掩码已固化 `/16`（第 11 篇） |
| **S90telnet** | 起 telnetd | 板子没 ssh，远程调试靠它 |
| **S99rtsp** | 起 sample_venc + 守护 | 166 行，本项目的"设备化"核心 |
| **守护进程（watcher）** | 监控子进程，挂了就重启 | `while true` + `wait` + 退避 |
| **单实例锁** | 防止启动两份 | 目录 + pid 文件；**必须放 tmpfs 且验 pid 存活** |
| **PID 复用** | 重启后 pid 号会被新进程占用 | 所以只用 `kill -0` 判断"是否在运行"会误判 |
| **退避重试** | 失败后等更久再试 | 连续失败 5 次 → 等 30 秒；连续 10 次 rc=255 → 判定池残留，直接 reboot 自愈 |
| **RTC** | 硬件时钟（带电池才能掉电走时） | 本板基本不可靠，靠 NTP |
| **hwclock -w / -u** | 把系统时间写进 RTC；`-u` 表示写 UTC | 必须 `-u`，否则内核按 UTC 读会快 8 小时 |
| **NTP / ntpd -q -n** | 网络对时；`-q` 对一次就退，`-n` 前台执行 | S99rtsp 里先补网关再对时 |
| **TZ / CST-8** | 时区；POSIX 格式，不依赖 zoneinfo | 必须 `export TZ=CST-8`，`/etc/TZ` 这个 busybox 不认 |
| **静态 IP / 掩码 / 网关** | 网络三件套 | 板 `/16` + `default gw 192.168.3.1` |
| **default route** | 默认路由，非本网段的包走它 | 没有它 → 能收不能回（"回包不通"） |
| **ARP** | 二层地址解析 | `arp -a` 有 MAC = 二层通，这是分层排障的起点 |
| **SIGTERM** | 可捕获的终止信号，进程有机会清理 | 脚本 `stop` **应该用这个**——`HandleSig` 才跑得到 `VB_Exit` |
| **SIGKILL（-9）** | 不可捕获的强杀，清理代码一行都执行不到 | 第 11 篇为"杀干净"全改 `-9`，直接导致 VB 池残留（第 12 篇 §06） |
| **优雅退出 / 清理链** | 停流→停 ISP→`SYS_Exit`→`VB_Exit`→退出 | 顺序不能乱；`SAMPLE_COMM_SYS_Exit()` 内含 `HI_MPI_VB_Exit` |
| **VB 池残留（rc=255）** | 上家被强杀，池留在内核模块 → 新进程 `HI_MPI_VB_SetConf failed` | **rc=255 是它的专属特征码**，只能 reboot 清（现已有自愈兜底） |
| **telnet** | 明文远程终端（23 端口） | 配合 Python 做自动化验证 |
| **tftp** | 极简文件传输（UDP 69） | 板↔VM 传二进制的唯一顺手方式 |
| **md5** | 文件指纹 | **验证"代码真的编进去了吗/传完整了吗"的唯一可靠手段** |

## 4 关键设计取舍：为什么这么做

这一节是全文最值钱的部分——**面试/评审时被问"为什么"就答这些**。

| 决策 | 选了什么 | 为什么不选另一个 |
|---|---|---|
| Sensor 驱动形态 | 用厂商 **用户态 `.so`** | 海思架构如此；换 `.so` 就能改行为，不必重编内核 |
| MIPI lane 配置 | `lane_id {0,2,-1,-1}` + `2+2` 分割 | 硬件实际走线是 lane0/lane2；控制器只支持 2+2 |
| 数据流转 | **bind**（除 NNIE 那一路） | 硬件直通，零 CPU 拷贝、延迟最低；user mode 每帧都要拷 |
| VB 池大小 | 48MB / 10 块 | 稳态只需 5 块，留一倍余量抗抖动；再大就挤占 MMZ |
| 码流存储 | **不落盘**（`VENC_SAVE_STREAM 0`） | 落盘会写满 tmpfs → 反压 → 掉帧（第 05 篇血案） |
| RTSP 实现 | **自己写 ~530 行** | live555 太重且功能受限；自研可控，出问题能改 |
| 传输方式 | UDP 单播（同时支持 TCP） | UDP 延迟低；TCP 在弱网更稳，做成可选 |
| OSD 挂接点 | **VENC chn0** | 只主码流需要；贴 VPSS 会同时影响子码流带宽 |
| OSD 硬件资源 | `OVERLAY_RGN` | 只需一块 200×40，内部 overlay 最快且不占带宽 |
| 字体方案 | **内嵌 8×16 点阵** | FreeType 要带库+字体几 MB，OSD 只需定字号 ASCII |
| 日志/锁位置 | **tmpfs** | 掉电即清，既不磨损 flash 也不会跨重启残留 |
| 守护策略 | 失败**退避重试**，不退出 | 无人值守设备"放弃"比"一直重试"更糟 |
| 停止方式 | **SIGTERM 优先，-9 超时兜底** | 只有 TERM 能让 `HandleSig` 跑完 `VB_Exit`；-9 会留下 VB 池残留（第 12 篇 §06） |
| 网关处理 | **候选探测 + 5 轮重试** | 写死会换环境就断；开机第一次 ping 必失败 |
| 时间同步 | NTP + `hwclock -w -u` | 无电池 RTC，只能靠网络；写 RTC 必须用 UTC |
| NNIE 接入方式 | 单独开 **VPSS chn2**（配 300×300，VPSS 对齐后实际 320×320） | 不能动主/子码流；模型只吃 300×300 |
| 检测结果呈现 | **全屏 ARGB1555 overlay + 每帧重绘** | 比动态改 RGN 尺寸简单；全屏画布一次建好，之后只改像素 |
| 检测线程节流 | **每 6 帧推理一次（≈5fps）** | 30fps 全推会占满 NPU 且没意义；人形变化没这么快 |

## 5 判据速查：出问题先看这几张表

### 5.1 帧率/画面异常的丢弃点

| 计数器 | 含义 | 指向 |
|---|---|---|
| VI `VbFail` | 申请不到 VB 块 | 下游不还缓存（反压） |
| VENC `Full` | 输入队列满 | 编码器被堵（输出侧） |
| VENC `BusyCnt` | 码流队列满 | 取流/写盘/发送太慢 |
| VENC `VencInt` 不涨 | 编码器没在编码 | 上游没给帧 |
| 检测线程 `GetChnFrame FAILED` | chn2 取不到帧 | VPSS chn2 没使能 / 第三池没建 |
| 进程启动即 rc=139 | 读 `u64VirAddr` 段错误 | 漏了 `HI_MPI_SYS_Mmap` |

### 5.2 网络分层判据

| 现象 | 结论 |
|---|---|
| `arp -a` 有 MAC | 二层通（网线、网口、PHY 都没问题） |
| ping 超时但 ARP 有 | 三层问题：IP/掩码/路由 |
| RX 涨 TX 不涨 | 收到了回不去 → 缺默认路由 |
| `ttl=128` 的回包 | 确实回到 Windows PC 了 |

### 5.3 进程/服务判据

| 现象 | 结论 |
|---|---|
| `ps` 有进程、`netstat` 没 554 | "残废进程"：bind 失败但没退出 |
| `stop` 后 3 秒又出现进程 | 老 watcher 没被杀，正在重启子进程 |
| `already running (watcher N)` 但 N 不存在 | 锁文件跨重启残留 |
| `/mnt` 有日志但编码器报错 | 双进程抢同一 VENC 通道 |
| `start` 报 `HI_MPI_VB_SetConf failed`、退出码 255 | 上一轮被 `kill -9` 强杀，VB 池残留在内核 → 只能 reboot |
| `ps` 里进程消失、日志里没有任何终止打印 | 进程是被 SIGKILL 杀的（handler 没机会跑） |

| **stop→start 可反复** | ✅ 优雅退出 rc=0、VB 池不残留、554 端口即起（第 12 篇 §06） |

### S2 已完成：NNIE 挂进现有进程（第 12 篇）

```
VPSS chn2 (320×320 YUV420SP)
   → GetChnFrame + HI_MPI_SYS_Mmap → 用户态读帧
   → CPU 转 BGR planar 300×300 → NNIE Forward（SSD .wk）
   → Ssd_GetResult（class15 person，阈值 0.5）→ 坐标反算 1920×1080
   → RGN overlay（layer=1，ARGB1555 全屏）→ VLC 里看到红框
```

三个必须记住的点：

| 坑 | 真相 |
|---|---|
| `u64VirAddr` 直接读 → rc=139 | `VB_REMAP_MODE_NONE` 下它是**内核地址**，必须 `HI_MPI_SYS_Mmap` |
| 红框上线后水印消失 | 本平台 overlay **layer 大者在上层，且透明像素替换下层**；水印 layer 必须 > 画框 layer |
| `stop` 后 start 永远失败 | 脚本 `kill -9` 跳过 `HandleSig` → VB 池残留；改 TERM 优先 |

### 还没做（按优先级）

1. **模型持久化**：`/mnt/nnie` tmpfs 重启即丢（当前降级 luma-only），需挪持久分区或开机 tftp 回灌
2. 断电重启终极验收（目前已通过软重启）
3. 多客户端并发、RTSP 鉴权、TCP 模式长稳、72h 压力
4. 专用人形检测模型（需 HiSVP_PC 工具包转 `.wk`）；检测框标签文字（可选）
5. 企业级缺口：ONVIF / GB28181 / 35114 / IQ 调优
6. 双摄（需第二颗摄像头，先确认 CSI0/CSI1 是并联还是各走一组 lane）
