## 知识地图：这条链路一共有七层

API 可以查，但"数据从哪来、到哪去、卡在哪一层"必须记在脑子里。
每一篇里都补了对应的原理小节（§x.y）：

| 层 | 要懂什么 | 详见 |
|---|---|---|
| sensor 与光学 | 曝光时间、行时间、3A、宽动态 | 02 §1.1 |
| MIPI-CSI + VI | 8/10bit、Bayer、lane 数、时序；海思架构 vs 设备树 | 02 §1.1、13 全篇 |
| VPSS | 多通道缩放、格式转换、OSD 叠加 | 01 §1.1、09 §0.1 |
| VENC | NAL/SPS/PPS、I/P/B、GOP、码控 | 04 §1.1 |
| 传输 | RTP/FU-A、RTSP、GB28181、WebRTC | 06 §2.1 |
| 存储 | jffs2/ext4/tmpfs 差异、MP4 封装 | 03 §4.1、05 §5 |
| 内存与时序 | VB 池、bind/user mode、PTS | 01 §1.1、05 §3.0 |

**贯穿所有层、真正拉开差距的三件事**：

1. **内存** —— 一帧 1080p NV12 就是 3.1MB；VB 池几块、MMZ 剩多少，必须心里有数
2. **时序** —— 时基在 `VB_FRAME.u64PTS` 里，不在文件里
3. **可观测** —— `/proc/umap/*` 是海思的黑匣子，出问题先看计数器，不要看 printf

> 判据：**基础知识学没学会，就看出问题时能不能一分钟内定位到层。**

## 五个最有价值的结论

### 1. 不要相信"成功"打印，要相信计数器

厂商库拔掉模组照样打 `GC2053 init succuss!`。可靠判据永远是 `/proc/umap/*` 里的计数：
`mipi_rx` DETECT INFO、`vi` 的 IntCnt、`venc` 的 VencInt。

### 2. 帧率问题要沿链路找"丢弃点"

三个丢弃点就是三处指纹：

| 计数器 | 含义 | 指向 |
|---|---|---|
| VI `VbFail` | VB 池申请失败 | 下游不还缓存（反压） |
| VENC `Full` | 输入队列满 | 编码器被堵（输出侧） |
| VENC `BusyCnt` | 码流队列满 | **取流/写盘/发送太慢** |

本次三个全中，一路追到 `fwrite` 卡 jffs2。

### 3. 嵌入式设备上，存储是最脏的环节

- `/tmp` 未必是 tmpfs（本板就是 jffs2）
- 分区快满时 jffs2 的 GC 会让写延迟从毫秒飙到**秒**
- 持续写百 KB/s 就能把采集链路压死
- **码流永远不写系统分区**：tmpfs / SD / NFS / 直接推流

### 4. 改代码必须用 md5 验证生效

`make clean` 不清 `../common/*.o`；二进制没变 = 白改。这条在排 MIPI 时浪费了大量时间。

### 5. 用对照实验划分责任

有厂商 demo 先跑厂商 demo。跑通 → 硬件无罪，问题在配置；跑不通 → 硬件/底层。把"N 种可能"压缩成"1 个方向"。
